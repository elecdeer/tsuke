# フェーズ5 設計: 紙のレシートを撮って登録する

## 目的

店で受け取った紙のレシートを、スマートフォンで撮影して支出として登録できるようにする。今は拡張機能（PC のブラウザ）からしか新規に登録できず、紙のレシートは手で打ち込むしかない。

## 前提

- 台帳の Web 画面（`apps/ledger`）を PWA にして、スマートフォンのホーム画面から開けるようにする。別のアプリは作らない
- 同じ Worker `tsuke` で動かす。Cloudflare Access の後ろにあるので、ログインは今までどおり Access が行う
- 撮影したら AI が日付・店舗・口座・品目を読み取り、確認フォームに入れる。人が直してから登録する（自動では登録しない）
- レシートの画像は登録したものだけ保存する（「画像の保存」を参照）
- オフラインでは使わない。通信できるときだけ使う

## 仕組み

### PWA

- `public/manifest.webmanifest` とアイコン（`public/icons/`）を置き、`void.config.ts` の `head` に `<link rel="manifest">`・`apple-touch-icon`・`theme-color` を足す
- `start_url` はレシートの登録の画面（`/receipts/new`）にする。ホーム画面から開く用途はほぼこれなので
- Service Worker は置かない。Android の Chrome も iOS の Safari も、manifest があればホーム画面に追加できる。オフラインで使わないので、キャッシュする理由もない
- manifest とアイコンも Access の後ろにある。manifest の `<link>` に `crossorigin="use-credentials"` を付けて Cookie を送らせる。それでもアイコンが取れない（ホーム画面のアイコンが出ない）場合は、Access に `/manifest.webmanifest` と `/icons/*` を Bypass するアプリケーションを足す（実機で確かめてから決める）

### 撮影と画像の送信

- `<input type="file" accept="image/*" capture="environment">` で端末のカメラを開く。カメラを独自に組まない（ピント・露出は OS のカメラの方が良く、ライブラリも要らない）
- 撮った画像はブラウザで canvas に描き、長辺 1600px の JPEG（品質 0.8）に縮めてから data URL で送る。スマートフォンの写真（数 MB）をそのまま送ると遅く、AI の入力トークンも増えるため。1600px あればレシートの小さい文字も読める
- 読み取りでは画像を `POST /api/receipts/extract` に JSON で送り、サーバーは AI に渡したら捨てる

### 読み取り（AI）

- 自動入力のモデルを `openai/gpt-6-luna` に変える（`env.ts` の `LLM_MODEL` の既定値）。拡張機能の自動入力も同じモデルになる
- `src/llm/extractReceipt.ts` を作る。出力のスキーマは拡張機能の自動入力と同じ `ExtractedPaymentSchema` を使い、プロンプトだけを紙のレシート向けにする（税込・税抜の扱い、値引きの行、合計・お預り・お釣りの行を品目にしない、など）
- `runStructuredChat` は今は文字のメッセージしか送れないので、user メッセージに画像（`image_url` の data URL）を足せるようにする
- `openai/gpt-6-luna` が Workers AI の binding で画像の入力と `json_schema` を受け付けるかは、Cloudflare のドキュメントに書かれていない。最初にスパイクで確かめ、だめなら画像に対応したモデルを別に `RECEIPT_LLM_MODEL` で指定する
- 評価スクリプト（`scripts/eval-extract-payment.ts`）にレシート画像の事例を足すのは今回はしない。実際のレシートで使ってみて、読み取りの誤りが目立ったら足す

### 読み取りのモデル（速さ優先と、読み直し）

- 撮ったらまず `google/gemini-3.1-flash-lite` で読む（`quality: "fast"`）。誤りが目立つときは、確認の画面の「もう一度読み取る」で `google/gemini-3.8-flash` の推論量 `low` で読み直す（`quality: "accurate"`）
- 拡張機能のページからの自動入力も同じにする。読み取った後に出る「もう一度読み取る」で読み直す。もともと自動入力を押し直すとフォームは上書きされるので、読み直しの前には確かめない
- モデルと推論量は `src/llm/readQuality.ts` の `READ_SETTINGS` に組で持つ。受け付ける推論量がモデルごとに違う（Gemini は `none` を受け付けない）ので、環境変数で片方だけ変えられないようにする。明細の読み取りは、引き続き `env.ts` の `LLM_MODEL` を使う
- 読み直しもキューを通すので、同時に頼む枚数の上限に数える。結果が届くまで前の結果を残し、失敗しても失わない。直した内容があれば、置き換わる前に確かめる
- 比較の結果（レシート 5 枚を各 5 回。時間は中央値）。`cf ai run` で測ったもので、1 回の料金は定価から計算した目安

| モデル（推論量）                           | 時間    | 合計 | 品名 | 1 回    |
| ------------------------------------------ | ------- | ---- | ---- | ------- |
| `google/gemini-3.1-flash-lite`（指定なし） | 2.05 秒 | 80%  | 84%  | $0.0011 |
| `google/gemini-3.8-flash`（`low`）         | 4.21 秒 | 100% | 100% | $0.0031 |
| `openai/gpt-6.1-terra`（`none`）           | 4.12 秒 | 100% | 100% | $0.0045 |
| `openai/gpt-6-luna`（`none`）              | 3.76 秒 | 76%  | 8%   | $0.0005 |
| `openai/gpt-6-luna`（`low`）               | 6.32 秒 | 100% | 28%  | $0.0005 |

ページからの読み取りの比較（`scripts/eval-fixtures/amazon.json` を各 10 回。事例はこの 1 件だけ）。日付・口座・店舗・品目数・金額はどのモデルも全回正しく、差は品名とメモだけだった。`gpt-6-luna` は品名を短くまとめ、`gemini-3.1-flash-lite` は品名を残すがメモを足すことがある

### 確認フォームと登録

- 新しいページ `/receipts/new`（`pages/receipts/new.tsx` と `new.server.ts`）
  - `loader`：口座・支出のカテゴリ・店舗の候補
- 読み取りは `POST /api/receipts/extract`、重複の確かめは拡張機能と同じ `POST /api/transactions/duplicates` を `createLedgerClient` で呼ぶ。Void のページのアクションは値を返せず（loader を走らせ直すかリダイレクトするだけ）、読み取った結果を画面に返せないため。同じ origin なので Access の Cookie はそのまま送られる
- フォームは取引の編集画面（`pages/transactions/[id].tsx`）の入力部品（品目の行・カテゴリの選択・口座の選択など）を `src/web/components/` に切り出して共有する。支出だけなので、向きや振替の欄は出さない
- 読み取りの結果は `src/web/transactionDraft.ts` の下書きに変換してフォームに入れる。読み取れなかった項目（`null`）は空のままにし、カテゴリが決まらない品目は登録の前に選ばせる
- 重複の候補があれば、拡張機能と同じくフォームの中に警告を出す（登録は止めない）
- 撮影した画像の縮小版を、フォームの横（狭い画面では上）に出して見比べながら直せるようにする

### レシートの部分だけを見せる

- 見比べるときに背景で文字が小さくならないよう、確認の画面の写真はレシートの部分だけを切り取って見せる。「全体を表示」で写真の全体に戻せる。切り替えはレシートごとで、次のレシートへ持ち越さない
- 範囲は読み取りと同じ呼び出しで AI に返させる（`receiptBox`）。呼び出しを増やさず、別の検出の仕組みも要らないため
- 座標は写真の左上を 0、右下を 1000 とする。ピクセルで頼むと、写真の大きさを伝えても多くの回で 0〜1000 の値が返ってきた
- 切り取りは表示だけで、登録する写真は全体のまま。傾いたレシートは範囲に背景が少し入る
- 速いモデルは範囲を最大で写真の 5% ほど狭く返したので、端が切れないよう四方に 5% の余白を足す
- 範囲が外れているとき（0〜1000 の外、逆転、狭すぎる）、ほぼ全体を指すとき、読み取る前と読み取れなかったときは、全体を見せて切り替えも出さない
- 比較の結果（合成した写真 6 枚。`cf ai run` で測った値。実際に撮った写真では測っていない）。0〜1000 は `runExtractReceipt` を通し、速いモデルは各 3 回、もう一方は各 1 回。ピクセルは項目を減らしたプロンプトで、それぞれ各 2 回と各 1 回。IoU は正解の範囲との重なり、不足は範囲からはみ出したレシートの長さの最大（写真に対する割合）

| 座標の指定 | モデル                  | IoU の中央値 | IoU の最小 | 不足の最大   |
| ---------- | ----------------------- | ------------ | ---------- | ------------ |
| 0〜1000    | `gemini-3.1-flash-lite` | 0.95         | 0.78       | 5.4%         |
| 0〜1000    | `gemini-3.8-flash`      | 0.99         | 0.98       | 0.2%         |
| ピクセル   | `gemini-3.1-flash-lite` | 0.36         | 0.16       | 測っていない |
| ピクセル   | `gemini-3.8-flash`      | 0.79         | 0.28       | 測っていない |

### 連続での読み取り（キュー）

- 撮った写真はキューに溜め、確かめている間も続けて撮れるようにする。カメラは 1 枚ずつしか撮れないので、撮りためた写真をまとめて選ぶボタンも置く
- AI の読み取りは裏で撮った順に進め、同時に頼むのは 2 枚まで（`READ_CONCURRENCY`）。続けて撮っても待ちが長くならず、Workers AI へ一度に頼みすぎない
- 読み取れたものから 1 枚ずつ確かめて登録する。登録すると取引の画面へは移らず、キューの次のレシートへ進む。登録した取引へは知らせの中のリンクから開ける
- 登録はページのアクションではなく、拡張機能と同じ `POST /api/transactions` で行う。アクションはリダイレクトしかできず、この画面に留まって次のレシートへ進めないため
- キュー（写真・読み取りの結果・入力中の値）はブラウザの IndexedDB に保存する（`src/web/receiptQueueStore.ts`）。画面を閉じたり読み込み直したりしても撮り直さずに済む。読み取り中のまま閉じたものは、開き直したときに読み直す。登録するまで写真は端末の中にだけ置く
- 読み取れなかったレシートは、読み直すか手で入力して登録できる。読み直しに失敗したときは、前の結果のまま直して登録できる。登録しないレシートは捨てられる

### 画像の保存

- 登録するレシートの画像を R2（`void/storage`、binding は `STORAGE`）に保存する。登録の `POST /api/transactions` に `receiptImage`（data URL）を付けて送る。拡張機能の登録には付かないので省略できる
- キーは `receipts/<UUID>.<拡張子>` にしてサーバーで決め、`transactions.receipt_image_key` に入れる。写真が 1 枚のレシートが取引 1 件に当たるので、1 取引 1 枚にする
- 先に R2 へ保存してから取引を入れ、取引を入れられなかったら画像を消す。逆の順だと、取引が存在しない画像を指すことがある。画像を保存できなければ登録もしない（画像はキューに残るので、登録し直せる）
- 画像は取引がある限り残す。取引を消すときに一緒に消す。消せなかったときはキーをログに出す
- 取引の編集画面に画像を出す。`GET /api/transactions/:id/receipt-image` が取引の ID から DB でキーを引いて返す
- カード番号の下 4 桁や購入内容が写っているので、バケットは公開せず（公開アクセスや r2.dev を有効にしない）、Access のミドルウェアの後ろのこのルートからだけ読ませる。`Cache-Control: no-store` にする。ブラウザに残すと、取引を消した後や Access からログアウトした後もサーバーを通らずに見えてしまうため

## 決めたこと

- **PWA は台帳の Web 画面に入れる。** 別のアプリにすると、Access のログインと CORS を拡張機能と同じように組み直すことになる。同じオリジンならページのアクションをそのまま使える
- **画像は登録したものだけ台帳に保存する。** 最初は保存しないことにしていたが、読み取った画像を見返せるように変えた。読み取りの時点で保存すると、捨てたレシートの画像を消す仕組みが要る。登録のときなら余分な画像が残らず、読み取りも遅くならない。確かめ終わるまでのキューとしては、端末の IndexedDB に置く
- **Service Worker は置かない。** オフラインで使わず、ホーム画面への追加にも要らないので

## 範囲外

- 登録しなかったレシートの画像の保存（読み取りの評価の材料にするなど）
- オフラインでの撮影と、後からの送信
- 1 枚の写真に写った複数のレシート、長いレシートを分けて撮った複数の写真
- 収入・振替の登録
- 撮影以外の新規登録（手入力だけのフォーム）。フォームは同じなので、必要になったら写真なしでも開けるようにする

## 作る順

1. スパイク：`openai/gpt-6-luna` に画像と `json_schema` を送れるか確かめる。`LLM_MODEL` の既定値を変える
2. `runStructuredChat` に画像を足し、`extractReceipt.ts` とテスト
3. 編集画面の入力部品を `src/web/components/` に切り出す（編集画面の見た目と動きは変えない）
4. `/receipts/new` のページ（撮影・縮小・読み取り・確認・重複・登録）
5. PWA（manifest・アイコン・head）とナビ。実機のホーム画面に追加して、Access のログインとアイコンを確かめる
